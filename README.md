# Amazon E-Commerce Platform — Production-Ready Full-Stack System

Build a real-world, scalable, secure, production-ready e-commerce platform inspired by modern marketplaces such as Amazon, using **Next.js 16 App Router, React 19, TypeScript, Tailwind CSS 4, Supabase PostgreSQL, Supabase Auth, Row Level Security (RLS), Redux Toolkit, Zod, Axios, and Vercel**, with a clean architecture that separates customer storefront, admin dashboard, and superadmin control panel; the system must support a complete customer journey including homepage, navigation, product catalog, categories, brands, search, advanced filtering and sorting, product details, image gallery with zoom, variants such as size/color, inventory-aware quantity selection, wishlist, persistent shopping cart, coupons, multiple addresses, checkout, payment selection, order creation, order tracking, shipment tracking, returns, refunds, reviews, notifications, profile management, password change, password reset, email verification, OAuth-ready authentication, and account deletion, while the admin dashboard must provide production-grade management for products, product variants, product images, categories, brands, collections, banners, menus, coupons, customers, users, orders, payments, refunds, returns, reviews, inventory, warehouses, stock movements, vendors, shipments, shipping methods, shipping rates, support tickets, blogs, FAQs, newsletter subscribers, notifications, security settings, application settings, audit logs, analytics, system health, and reports; implement a dedicated superadmin area with complete user management, admin management, role management, permission management, security controls, audit-log access/export, system configuration, and unrestricted administrative capabilities, using a granular RBAC permission model such as `products:view`, `products:create`, `products:update`, `products:delete`, `orders:view`, `orders:update`, `users:view`, `users:update`, `inventory:adjust`, `settings:update`, etc., where customer, admin, and superadmin roles have clearly separated privileges and server-side authorization is always treated as the source of truth; use the architecture **Browser → Next.js Server/Client Components → Next.js API Layer → Server Handlers/Services → Supabase PostgreSQL/Auth/Storage**, with the frontend built using the Next.js App Router and server-side rendering for SEO-sensitive pages, client components only where interactivity is required, reusable UI components, responsive layouts, accessible forms, loading states, skeletons, empty states, error boundaries, 404/403 pages, toast notifications, optimistic UI where appropriate, mobile-first design, keyboard accessibility, semantic HTML, proper focus management, and consistent design tokens; implement a centralized API architecture where `/api/[...path]/route.ts` receives requests and dispatches them through a typed router to dedicated authentication, storefront, product, admin, dashboard, inventory, order, payment, shipment, user, and generic resource handlers, with every API returning a consistent response structure such as `{ success: true, data, message, meta }` or `{ success: false, error: { code, message, details }, requestId }`, correct HTTP status codes, centralized error handling, request IDs, structured server logging, Zod validation, pagination, filtering, sorting, search parameters, API versioning readiness, and protection against malformed or unexpected requests; authentication must use Supabase Auth with secure session handling, access/refresh token lifecycle management, email verification, password reset, optional Google OAuth, logout, account deletion, session expiration, blocked/suspended account checks, secure cookies where appropriate, and server-side user verification, while the Supabase service-role key must exist only in trusted server-side code and must never be exposed to the browser, source repository, client bundle, logs, or public environment variables; implement PostgreSQL using normalized relational tables for profiles, roles, permissions, role_permissions, products, product_variants, product_images, categories, brands, collections, collection_products, carts, cart_items, wishlists, addresses, orders, order_items, payments, payment_transactions, coupons, coupon_usages, warehouses, stock, inventory_movements, shipments, shipment_events, shipping_methods, shipping_rates, returns, return_items, refunds, reviews, vendors, support_tickets, notifications, banners, menu_items, blogs, FAQs, newsletter subscriptions, app_settings, security_settings, audit_logs, security_events, idempotency_keys, and related entities, using UUID primary keys, foreign keys, unique constraints, check constraints, timestamps, soft deletion where business requirements justify it, appropriate indexes, database functions, triggers, transactional operations, and strict referential integrity; design inventory as a real transactional system using atomic PostgreSQL operations and a **reserve → commit → release** workflow so concurrent checkouts cannot oversell stock, maintain inventory movement history for every adjustment, reservation, sale, return, cancellation, and manual change, support multiple warehouses, warehouse-specific stock, low-stock thresholds, inventory policies, SKU/barcode management, and stock reconciliation; implement checkout as an idempotent transactional workflow that validates the authenticated customer, address, cart contents, product availability, variants, pricing, coupon eligibility, taxes, shipping charges, discounts, inventory, and payment method before creating the order, reserving inventory, recording payment information, clearing the cart, generating order numbers, and creating audit/events, with an `idempotency_keys` mechanism preventing duplicate orders when users double-click checkout, refresh pages, retry requests, or experience network failures; support payment architecture that initially allows Cash on Delivery while remaining ready for Stripe, PayPal, JazzCash, Easypaisa, or other gateways through a provider abstraction, storing payment intent/transaction references safely without storing raw card information, and use webhook endpoints for asynchronous payment confirmation with signature verification, idempotency, replay protection, and transaction-safe status updates; implement shipping with configurable shipping methods, shipping rates, warehouse assignment, shipment records, tracking numbers, shipment events, status history, estimated delivery dates, and customer/admin tracking interfaces; implement a robust order state machine such as `pending → confirmed → processing → packed → shipped → out_for_delivery → delivered`, with cancellation, return, refund, and payment states handled independently rather than relying on one overloaded status field; implement coupons with percentage/fixed discounts, minimum order amounts, usage limits, per-user limits, expiration dates, active/inactive states, applicable products/categories/collections, and transactional usage tracking; implement product management with SEO-friendly slugs, SKU, barcode, pricing, sale pricing, cost price, descriptions, short descriptions, brand, category, variants, images, stock configuration, weight, dimensions, tax configuration, shipping requirements, featured status, tags, metadata, SEO title/description, canonical URL support, and active/draft/archived states; use Supabase Storage for production product images and other media where appropriate, generate optimized responsive images through Next.js image optimization, validate uploads by MIME type and file size, prevent unsafe file uploads, and avoid relying on fragile external image URLs for core business data; use Redux Toolkit only for genuinely client-side global state such as cart UI state, wishlist state, authentication presentation state, filters where necessary, and transient UI state, while avoiding duplication of server state unnecessarily and using server fetching or a suitable data-fetching/cache layer for server-owned data; if Redux Persist is used, persist only safe non-sensitive client state and never persist service-role keys, passwords, payment credentials, or unnecessary authentication secrets; create a reusable component system containing buttons, inputs, selects, dialogs, dropdowns, tables, pagination, forms, modals, badges, cards, product cards, product galleries, skeleton loaders, error states, empty states, confirmation dialogs, status indicators, navigation, sidebar, header, footer, breadcrumbs, responsive tables, and accessible form controls; implement data tables with pagination, server-side search/filtering/sorting, bulk actions, confirmation dialogs, export capabilities, column visibility where useful, loading states, error recovery, and responsive mobile behavior; implement audit logging for all sensitive administrative operations, recording actor ID, action, resource type, resource ID, timestamp, IP address where legally appropriate, request ID, before/after information where safe, and relevant metadata, while avoiding passwords, access tokens, payment credentials, or other secrets; implement security using Supabase RLS as defense-in-depth, server-side authorization, least-privilege access, secure cookies, strict CORS where applicable, CSRF protection where applicable, security headers including Content-Security-Policy, X-Content-Type-Options, X-Frame-Options or CSP frame-ancestors, Referrer-Policy, Permissions-Policy, HSTS in production, rate limiting, brute-force protection, input validation, output encoding, SQL injection protection through parameterized queries/Supabase APIs, XSS protection, open-redirect protection, secure file-upload validation, webhook signature verification, request-size limits, environment-variable validation, secret isolation, dependency auditing, and protection against IDOR/BOLA by always checking resource ownership and permissions server-side;
